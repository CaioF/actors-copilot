# Affiliate coupon QA

## Recorded production observation

On 2026-11-18 in isolated headless Chrome against `app.theactorscopilot.com`, an authorized Free test identity followed the Lucas referral, selected monthly Economy, and opened Stripe Checkout. The checkout displayed LUCAS, a 20% first-cycle discount, 14 days free, USD 0.00 due today and USD 15.20 after the trial. No payment or subscription was completed. Opening checkout can create or reuse a real Stripe customer and checkout session for that test identity.

The operator panel displayed Lucas's coupon and `/login?ref=lucas` link. Because checkout was not completed, the observed panel state is a baseline, not evidence that this visit created an attribution. The original example's starting counts and signup instructions are not assumed to be current.

The local recording `evidence/qa-affiliate-flow.webm` concatenates four clips; it is not one uninterrupted recording. The recording and source clips are intentionally Git-ignored. Authentication was performed off-camera. The first clip contains an explicitly labeled QA overlay reflecting the browser's referral storage. The Stripe clip is cropped to remove the contact and payment form. The admin clip hides other affiliates, contact details and real account counts and financial totals because this repository is public. No card details were entered.

The reference-link discount and panel display were observed. Manually entering a coupon, completing checkout, webhook delivery, a new referral count, payments and real commissions were **not** verified by this recording. The automated unit/integration tests use mocks at external boundaries and are not evidence of those live effects.

## Controlled simulation after deployment

`POST /api/admin/affiliate-qa` simulates a trial for a pre-existing, explicitly allowlisted Firebase identity and affiliate. It is disabled unless `QA_SIMULATION_ENABLED=true`; a valid admin session and a separate 64-hex-character secret are both required. UID and the Firebase account email must each match their allowlists. An active/trialing subscription, an existing subscription ID, a real active/trialing Stripe subscription, or any nonzero paid invoice causes rejection. A conflicting existing affiliate or another active simulation is also rejected. The endpoint performs Stripe **reads** but does not create a Stripe subscription, payment, invoice or signed webhook event.

Before writing test entitlements, the endpoint verifies the test identity token and checks the effective Firestore client permissions with a positive control, a read probe and a write probe with an impossible precondition. Any unexpected response or inability to verify blocks the simulation. Production QA is currently disabled because the rules check did not pass. Merging this PR alone is not sufficient to activate the test.

The simulation writes marked test-only trial and attribution fields to the allowlisted account, stores a signed server-owned snapshot, and displays QA referrals separately from real counts and revenue. The member list labels the test membership. A simulated platform session lasts at most 15 minutes; cleanup does not revoke an already-issued token immediately. Disabling the feature rejects QA sessions, but changing Vercel environment values takes effect on a subsequent deployment. Cleanup restores only fields written by the simulation and refuses to overwrite concurrent changes. Clean up active runs before rotating the signing key; otherwise their snapshots cannot be authenticated automatically. Never use the same test account for a real checkout while a simulation is active. A cleanup failure requires manual review, not a blind retry or an overwrite of Stripe state.

This is an approximation for QA, **not** an invocation of the signed Stripe webhook. It can verify the application's simulated entitlement, attribution and admin presentation, but cannot prove real payment, actual Stripe subscription creation, signed webhook delivery or production commission accounting. Those boundaries need an independent Stripe test-mode or authorized live-payment test.

### Configuration and execution

1. Install dependencies with `pnpm install --frozen-lockfile`. Install Chrome and FFmpeg separately. Set `AC_CHROME_PATH`, `AC_FFMPEG_PATH`, the authorized test account's `AC_TEST_EMAIL`/`AC_TEST_PASSWORD`, and the target Firebase public API key via environment variables. Do not place credentials in a committed file or recording.
2. Run `node qa/affiliates/setup-local.mjs` once. It verifies the test identity and writes an ignored `.env.qa.local` containing a random 256-bit secret and allowlists for that single UID, email and Lucas. It refuses to overwrite an existing file. Keep the file private.
3. Configure the five `QA_SIMULATION_*` variables as sensitive server-side Vercel variables for the intended deployment, leaving `QA_SIMULATION_ENABLED=false`. The secret necessarily exists both locally and in the deployed server environment; it must not be sent in a URL, printed or committed. The repo's Firestore rules explicitly deny client access to the QA collection; deploying Firestore rules is separate from the Vercel merge and must be handled through the project's established rules workflow.
4. Verify the effective rules with `node qa/affiliates/check-qa-rules.mjs` using the approved test identity and public Firebase configuration. It checks read and write denial with a positive control and never creates a document. Do not enable the simulation until this check passes and the rules deployment has been independently reviewed. Then enable the flag for a subsequent deployment. Disabling it again also requires a subsequent deployment.
5. After the reviewed PR and correctly configured deployment are ready, set `AC_ADMIN_USERNAME` and `AC_ADMIN_PASSWORD` in the current process, plus the test identity variables above. Run `node --env-file=.env.qa.local qa/affiliates/run-simulation.mjs` with `AC_QA_SOURCE=link` or `coupon`. The script checks the simulated member session, records the labeled admin row, and attempts cleanup in `finally`. Do not run both modes concurrently on the same identity. Review any cleanup failure before continuing.

The recording scripts require `puppeteer-core` and FFmpeg. `record-public-referral.mjs` captures the isolated referral form. `record-referral.mjs` opens a real checkout without completing it, and `record-admin.mjs` records the selected admin row after logging in off-camera. Inspect all generated video before sharing; UI changes can invalidate redaction. Never commit recordings. Never record authentication entry, payment details, unrelated members or unredacted checkout forms.
