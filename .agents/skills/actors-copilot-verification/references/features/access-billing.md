# Access and billing

## Entry and behavior

- `/login`: switch Log In / Create Account, email/password or Google, password visibility, remember-me, forgotten password. Check validation, loading, errors and resulting navigation; do not create an account against an unknown backend.
- Login callback exchanges Firebase identity for a platform session (`lib/context/AuthContext.tsx`, `app/api/auth/callback/route.ts`). Both client auth and server cookie matter. Test signed out, expired/invalid session and reload; logout should remove access.
- `proxy.ts` matcher protects specified routes, not every path in the interior group. With Stripe engine, missing/invalid session redirects to login; free or inactive sessions are allowed on dashboard and otherwise routed to upgrade on matched paths; active economy is redirected from profile and acting coach; active business passes. `/api/billing/success` and admin have special handling. Check the actual matcher and `ProtectedRoute` separately before asserting protection for `/reader-copilot`, `/dna-vault` or `/upgrade`.
- `/upgrade` chooses plan and calls checkout; `/settings` opens billing portal. `/start-trial` handles flagged recovery and calls recovery checkout. Test success, cancellation, repeat request, recovery error and return to the same origin only in a verified Stripe test environment. A redirect to Stripe alone does not prove entitlement: confirm a real test subscription and webhook result, then refresh the session and check access.
- `/admin-dashboard` has a separate admin session and login; admin APIs require that session. Members and affiliates are sensitive administrative data; use isolated fixtures.

## Boundaries and checks

Stripe webhook owns access/tier/status; never manufacture entitlement by Firestore writes. Checkout must reuse mapped customer and preserve idempotency. Check test-mode price configuration, origin and webhook signing; do not submit live payment or mutate a real subscription. Recovery state lives on the user record and is cleared when a real subscription exists. Account deletion is destructive and is not a smoke-test step.

## Concrete UI and state transitions

1. On `/login`, choose **Log In** or **Create Account**. Email and password fields, visibility toggle, Keep me signed in, Forgot password and Google are separate paths. Blank password reset requests should show a validation message without sending email. Signup and password reset can create an account or send mail: exercise only with an explicitly authorized test account. Firebase sign-in and the server session callback are separate steps.
2. When signed out, navigate to `/dashboard` and expect `/login` for the matched proxy route. For a real active Economy session, open `/profile` and `/acting-coach`; both redirected to `/upgrade` in the 2026-11-17 production browser run. Reader, auditions, DNA Vault and settings opened for the same account. These observations used a session seeded through the real callback; they do not establish normal login or Business behavior.
   A separate authorized Free account, using the same session setup, reached `/dashboard`; `/chat`, `/auditions`, and `/profile` each redirected to `/upgrade`. This checks those routes only, not every member route.
3. At `/upgrade`, inspect Monthly/Annual, USD/EUR/GBP controls and the plan buttons. An Economy session displayed `Current Plan` and `Upgrade to Business Class`. Switching cycle/currency changes displayed prices and availability; check disabled reasons, not just visual color. Source routes monthly selection through `/api/billing/checkout`, while annual uses fixed Stripe payment links. Do not assume both use the same checkout API or complete a real payment as a smoke check.
4. `/start-trial` is the recovery interstitial; check the recovery flag returned by callback, countdown and error/retry separately from successful Stripe subscription creation. The webhook clears the flag after subscription establishment. A redirect or UI message is not evidence of entitlement.
5. `/settings` → Subscription & Billing shows plan and status and, for active/trialing sessions, **Manage Subscription**, which calls `/api/create-portal-session`. Portal navigation can affect a real subscription; opening or changing it must match the current test scope. Admin uses an independent `/admin-dashboard` username/password form and `admin_session` cookie; a member cookie does not establish admin access.

**Observed plan controls, 2026-11-17.** In production, Chrome 157 headless at 1440×900 with independently seeded Economy and Free test sessions: selecting EUR, GBP and USD updated the currency radio state and both plan cards showed the corresponding currency symbol. Annual showed `/year` and the annual-billing note; returning to Monthly showed `/month` and removed that note. The browser counted zero POSTs to `/api/billing/checkout` during these interactions. No checkout button, payment link, Stripe portal, actual amount, tax, promotion, payment availability or entitlement transition was tested; successful display is not proof that a currency can be purchased.

**Authentication diagnostic.** On 2026-11-17 ordinary UI login with a valid Economy account entered an apparent login/dashboard loop in the integrated browser and once in headless Chrome. Server-side test of Firebase sign-in → POST callback → GET callback with its real cookie → dashboard returned success. The observation does not isolate a root cause or establish prevalence. Reproduce in a fresh normal browser, inspect callback and redirect timing with CDP while redacting tokens and cookies, and report the actual browser and deployment. The opt-in seeded setup in [browser automation](../browser-automation.md) unblocks feature exploration but bypasses this verification.

After PR #114 reached production (`dpl_75UfhS9Y2MTRC4gwnHNRVeteXxbh`), a separate authorized Free account in a fresh headless Chrome 157 session stayed on `/login` for the inspector's 30-second limit. Its response observer counted 28 `GET /api/auth/callback` responses with status 401 and observed no completed POST callback response during that window. This is one browser run, not evidence that every account is affected. The observed sequence is consistent with a session/redirect race, but does not prove why the POST response was not observed.
